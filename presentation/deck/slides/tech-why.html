Tech stack · Why these choices

Every tool has a reason

Browser-only phones

Any phone joins with a code or QR. No app to install.

Our own gateway

Windows has no tc; a Node.js shaper runs anywhere and is easy to measure.

Probes in the data queue

Latency is what the slice’s own traffic really waits.

Real elapsed time

Rates use the real clock, so Windows timer jitter doesn’t change them.

A 1 Mbps link

Seven phones can overload it; the hotspot never becomes the bottleneck.

Zod on every API

One schema gives validation and the type; bad input is rejected.

Same decision engine as our simulation study, now driven by measured traffic.

Each choice was made for a reason. Phones only need a browser: any phone can join by typing a code or scanning a QR, with nothing to install. We wrote our own gateway because Windows has no Linux-style traffic control, and a Node.js shaper runs on any laptop and is easy to instrument. Latency probes go through the same queue as the slice’s data, so the latency we report is exactly what that slice’s traffic waits. Rates are computed from real elapsed time, so the uneven Windows timers do not change them; we measured the shaper within a quarter of a percent of its limit. The link is scaled to 1 Mbps so seven phones can overload it while the Wi-Fi itself stays far from full. And every API input is checked with Zod.
